## 整体目标与推进顺序

用户于 2026-11-20 确认保留原始完整目标：资料获取（RSS、搜索、指定链接）→ AI 写作/改写/配图 → 人工编辑 → 微信草稿及知乎、小红书内容导出与后续接入。下面 P0–P5 仍是第一阶段计划，不代表完整产品范围。

当前先完成 P4 的普通文章到微信草稿闭环及对应验证，再开展资料获取与 AI。P5 的恢复、部署与真实平台验收继续保留；缺少真实账号条件时，平台验收仍记录未执行，不以模拟通过代替。

队列继续使用 PostgreSQL 持久任务表；采集和 AI 接入本身不要求 Redis。出现明确需求且现有方案经验证不适合后再评估，具体取舍见 [队列架构决策](adr/0001-postgresql-task-queue.md)。

## 阶段门槛

1. SPEC：确认用户目标、范围、非目标和验收标准。
2. PLAN：确认技术设计、依赖顺序、验证方案与已知限制。
3. IMPLEMENT：按里程碑实施，变更需求先回写 SPEC/PLAN。
4. VERIFY：执行检查并报告已通过/失败/未执行，不以模拟测试替代真实平台验证。
5. RELEASE：整理运行文档、升级/恢复方式与发布包，不自动公开 GitHub 仓库或发布外网。

## 后续产品路线（方向已确认，尚未实施）

1. 资料获取：RSS、搜索和指定链接，先细化输入、资料保存、网络访问与验收规则。
2. AI 创作：写作、改写与配图，产物进入现有文章编辑、修订和素材流程；服务商、模型和任务处理在该阶段确定。

这些方向在微信草稿闭环之后推进，尚未承诺版本、日期或已实现能力；每阶段先细化 SPEC 与验收再编码。自动选题与周期生成仍待需求确认，不因本轮保留整体架构而自动加入范围。

## 已知限制与处理

- 尚无用户公众号凭证：先验证模拟链路，真实验收保持待执行。
- 部署面向标准 Docker/Compose，不绑定 NAS 型号；镜像与引擎架构需匹配，未承诺所有平台均已实测。
- 第三方接口并不保证新增草稿幂等：不确定状态需人工核对，避免盲重试。
- 微信新版官方文档已在 P4 读取并核验，原文未精确定义的字符/字节细节采用明确记录的保守口径；实际账号权限和微信后台效果仍待验收。
- 单 Worker 是当前部署约束；明确的吞吐、多 Worker、任务隔离、优先级或延迟执行需求触发后续评估，不预设 Redis/BullMQ 迁移日期。
- 没有远程素材清理与本地垃圾回收：可能积累未引用文件或远程素材，交付说明写明人工维护方式。
- 原有代码在需求定稿前产生：只视作候选脚手架，测试和验收从零记录。
