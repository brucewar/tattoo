## 已实现

- 停止所选项目的 Web、API、Worker 后，流式保存 PostgreSQL 16 自定义归档和素材 ustar；主密钥、部署配置和镜像单独保管。完成校验后才生成 manifest，拒绝覆盖已有输出。
- 恢复前检查文件大小/SHA-256、归档路径与链接、持久和解析后的禁写配置、主密钥指纹及对应应用镜像 ID。只导入空数据库和空素材卷，不提供强制覆盖。
- 恢复后校验账号解密、撤销旧会话，将旧 QUEUED/RUNNING 意图及运行中 attempt 转为 UNCERTAIN 并记录轨迹；已有终态保持。仅 PostgreSQL 运行，API/Worker 不自动启动。
- 增加从账号配置到图文、预览、草稿和记录的完整浏览器流程，以及权限拒绝后明确修复建议和显式重试。

本机环境：Windows、Node.js 22、Chromium；Docker Engine 28.4.0、Compose 2.39.2-desktop.1，Linux/amd64 引擎。本机正式构建止于基础镜像元信息请求，完整 Docker 构建与运行证据来自对应 CI。

恢复验收入口为 `npm run verify:recovery`，在已构建应用/Web 镜像后执行。脚本需要 Docker 发布端口可由管理电脑的环回地址访问，适用于本地 Engine、Docker Desktop 与 CI；这项验收不自动配置远程 Docker 连接。生产备份/恢复工具本身通过 Docker context 的流式命令操作目标容器，不要求远端共享管理电脑路径。

脚本在随机且受范围校验的两个 Compose 项目中执行：真实 HTTP 创建账号、图片及六份修订；准备五种投递状态；调用真实备份和恢复 CLI；检查错误密钥、启用写入、损坏归档和已有输出拒绝；恢复后检查账号解密、图文/历史/映射/远程 ID、会话撤销、旧任务冻结和非空目标拒绝；仅启动 API/Web 后验证旧会话失效、写入被拒和容器重建持久化。最终删除本次隔离项目及临时文件，不操作真实项目。

本地浏览器首次运行因权限错误文字同时出现在提示和事件记录中，测试定位不唯一；收窄到错误提示后，两项新增 P5 流程均通过。第二次本地运行合计 13 项通过、1 项旧 P4 用例超时：保留 trace 显示新页面创建耗时 48.7 秒，占用 60 秒总预算，任务结果断言仅获得 1.95 秒；失败 Worker 关闭浏览器另耗时约 125 秒。未放宽业务断言，完整 14 项以本次 Linux CI 的通过结果为准。

后续复测在 [诊断 CI](https://github.com/brucewar/tattoo/actions/runs/44706435893) 捕获到窄屏下公众号菜单退出动画仍位于页面根部，滚动时把页面宽度从 390 撑到 436，350 毫秒后恢复。投递菜单现改为挂载在对话框内部，浏览器回归逐帧检查选择与滚动期间的最大页面宽度。另以真实登录响应暂缓返回，复现加载图标将按钮可访问名称改成“loading 登录”；登录按钮现保持固定名称，并保留加载状态语义。未延长业务超时或隐藏横向溢出，临时三轮 CI 循环及页面几何日志已移除。修复后使用锁文件对应 Chromium 159 在本机运行完整 14 项，全部通过，独立服务、schema 和临时素材清理成功；前端类型检查与生产构建通过。

## 交付边界

本轮不要求指定 NAS 验证；镜像与 Docker 平台必须匹配，未实测平台不宣称通过。首版恢复要求 PostgreSQL 16 与备份对应的精确应用镜像，不承诺跨 CPU 架构恢复。

AT-09 仍需用户在自己的部署环境配置 AppID/AppSecret 与白名单，显式发起草稿并查看微信后台；不要在聊天中提供密钥。真实验收未执行时，只能交付候选版本，不能宣布第一阶段全部验收完成。
