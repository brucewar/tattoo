# P5 Docker 运维与恢复验收

日期：2026-11-20。部署边界按用户本轮决定调整为标准 Docker Engine / Compose，不要求指定 NAS 型号、内存或实机验收。真实微信公众号验收仍独立保留。

## 已实现

- 停止所选项目的 Web、API、Worker 后，流式保存 PostgreSQL 16 自定义归档和素材 ustar；主密钥、部署配置和镜像单独保管。完成校验后才生成 manifest，拒绝覆盖已有输出。
- 恢复前检查文件大小/SHA-256、归档路径与链接、持久和解析后的禁写配置、主密钥指纹及对应应用镜像 ID。只导入空数据库和空素材卷，不提供强制覆盖。
- 恢复后校验账号解密、撤销旧会话，将旧 QUEUED/RUNNING 意图及运行中 attempt 转为 UNCERTAIN 并记录轨迹；已有终态保持。仅 PostgreSQL 运行，API/Worker 不自动启动。
- 增加从账号配置到图文、预览、草稿和记录的完整浏览器流程，以及权限拒绝后明确修复建议和显式重试。
- 补齐 [运维说明](OPERATIONS.md) 和 [AT 验收索引](ACCEPTANCE.md)。

本机环境：Windows、Node.js 22、Chromium；Docker Engine 28.4.0、Compose 2.39.2-desktop.1，Linux/amd64 引擎。本机基础镜像拉取失败不视为构建通过，也不通过修改镜像来源或已有部署绕过。

恢复验收入口为 `npm run verify:recovery`，在已构建应用/Web 镜像后执行。脚本需要 Docker 发布端口可由管理电脑的环回地址访问，适用于本地 Engine、Docker Desktop 与 CI；这项验收不自动配置远程 Docker 连接。生产备份/恢复工具本身通过 Docker context 的流式命令操作目标容器，不要求远端共享管理电脑路径。

脚本在随机且受范围校验的两个 Compose 项目中执行：真实 HTTP 创建账号、图片及六份修订；准备五种投递状态；调用真实备份和恢复 CLI；检查错误密钥、启用写入、损坏归档和已有输出拒绝；恢复后检查账号解密、图文/历史/映射/远程 ID、会话撤销、旧任务冻结和非空目标拒绝；仅启动 API/Web 后验证旧会话失效、写入被拒和容器重建持久化。最终删除本次隔离项目及临时文件，不操作真实项目。
